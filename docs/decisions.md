# 결정 기록

## 2026-11-02 -- Langfuse 관측 실습은 friend-agent 저장소에서 한다
선택: Langfuse 실습을 LLM 에이전트인 이 저장소(friend-agent)에서 한다. 로컬 실행은 uv 로 만든 Python 3.13 가상환경(.venv)과 claude-haiku-5-5 모델로 한다. 버린 대안: 다람쥐 정원(Squirrel-Garden)에 LLM 기능을 새로 넣고 계측, 개념만 정리.
이유: 다람쥐 정원에는 LLM 호출이 없어 트레이스에 남을 모델 호출, 토큰, 비용이 없다. 교안의 문제 상황(날씨 도구, 기억, 요금)이 이 저장소의 구조와 그대로 맞는다. 기본 모델(claude-opus-5-5)은 한 메시지에 3~4번 불리는 실습에 비용이 커서 haiku 로 낮췄다.
다시 볼 조건: 다람쥐 정원에 LLM 기능을 넣게 될 때, haiku 로는 도구 선택 품질이 실습에 쓰기 어려울 만큼 낮을 때.

## 2026-11-02 -- 트레이스에는 원문을 보내되 보내기 전에 패턴을 가린다
선택: 사용자 메시지, 모델 입력과 답, 기억 메모는 원문으로 Langfuse 에 보낸다. 다만 Langfuse SDK 의 마스킹으로 전화번호, 이메일, 카드 번호, API 키처럼 보이는 문자열은 보내기 전에 가린다. 서버 로그에 원문을 남기지 않는 기존 규칙은 그대로 둔다. 버린 대안: 원문 그대로 보내기, 원문을 빼고 길이와 개수만 보내기.
이유: 원문이 없으면 엉뚱한 답이 도구 실패 때문인지 모델이 지어낸 것인지 읽을 수 없다. Langfuse 는 접근할 수 있는 사람이 정해진 관측 도구이고, 흔한 개인정보 패턴만 가려도 노출 위험을 크게 줄인다.
다시 볼 조건: 서비스를 실제로 공개해 다른 사람의 대화가 쌓이기 시작할 때(보관 기간과 개인정보처리방침 문구를 함께 정한다), 가려지지 않은 개인정보가 트레이스에서 발견될 때.

## 2026-11-02 -- Langfuse 세션은 사용자 ID 와 한국 날짜로 나눈다
선택: session_id 를 "사용자 ID + 한국 날짜(YYYY-MM-DD)" 로 만들어 한 사람의 하루치 대화를 세션 하나로 본다. 버린 대안: 마지막 대화에서 6시간 넘게 쉬면 새 세션.
이유: 이 서비스에는 대화방이 따로 없고 대화가 계속 이어진다. 날짜로 나누면 저장소를 더 읽지 않아도 되고, "어제 저녁" 같은 제보를 날짜로 바로 찾을 수 있다.
다시 볼 조건: 자정 전후로 이어지는 대화를 한 묶음으로 봐야 할 때, 사용자 시간대가 한국 밖으로 넓어질 때.

## 2026-11-02 -- Langfuse 계측을 staging 에 올려 리비전별로 비교한다
선택: langfuse-tracing 브랜치를 push 하고 staging 대상 PR 로 머지해 friend-agent-staging 에 배포한다. Langfuse 비밀키는 사용자가 콘솔에서 Secret Manager 의 langfuse-secret-key 로 만들고, friend-agent-runtime 계정에는 이 시크릿 하나의 읽기 권한만 준다. 공개키와 접속 주소는 일반 환경변수로 넣는다. 배포는 기존 deploy.yml(소스 배포)을 그대로 쓴다. 버린 대안: 로컬에서 version 값을 바꿔 두 버전 흉내 내기, staging 건너뛰기.
이유: "업데이트한 뒤로 느려졌다"를 확인하려면 실제 리비전 이름(K_REVISION)이 다른 트레이스가 필요하다. 배포 계정, WIF, staging 환경 변수가 이미 준비되어 있다.
다시 볼 조건: production 에도 키를 넣을 때(트레이스는 environment=production 으로 따로 쌓인다), 교안 G 항목처럼 Actions 에서 이미지를 만드는 방식으로 바꿀 때.

## 2026-11-02 -- 배포 단계에 --clear-base-image 를 더한다
선택: deploy.yml 배포 단계 flags 에 --clear-base-image 를 더해, 서비스에 남은 "기본 이미지(base image)" 설정을 배포 때마다 지운다. 버린 대안: 두 서비스에서 gcloud 로 한 번만 지우기.
이유: friend-agent, friend-agent-staging 은 처음에 Dockerfile 없이 소스 배포(기본 이미지 사용)로 만들어져 build-base-image 설정이 남아 있다. 저장소에 Dockerfile 이 들어온 뒤 staging 배포가 "Base image is not supported for services built from Dockerfile" 로 멈췄고, production 에도 같은 설정이 남아 있어 main 머지 때 똑같이 멈춘다. 워크플로에 적어 두면 두 환경 모두 풀리고 이유가 코드에 남는다. 사용자가 추천안을 선택.
다시 볼 조건: 교안 G 항목처럼 Actions 에서 이미지를 만들어 image 로 배포하도록 바꿀 때(이 옵션이 필요 없어진다).

## 2026-11-02 -- 화면 반응은 메시지 meta 의 트레이스 ID 로 잇고, /api/feedback 을 새로 만든다
선택: 답을 저장할 때 meta 에 Langfuse 트레이스 ID 를 함께 넣고, 반응이 오면 서버가 (로그인한 사용자, 메시지 ID)로 메시지를 찾아 트레이스 ID 를 꺼낸다. 좋아요, 별로예요는 새 API /api/feedback 으로 받아 user-feedback(BOOLEAN 1/0) 점수로, 기존 /api/report 는 주소와 입력을 그대로 두고 report(BOOLEAN 1) 점수와 사유(comment, 마스킹)를 더 보낸다. 저장소에 get_message(uid, id) 를 더한다. 버린 대안: done 이벤트에 트레이스 ID 를 실어 화면이 들고 있기, /api/report 하나로 반응 종류를 받기.
이유: 서버가 찾은 메시지에서 트레이스 ID 를 꺼내므로 브라우저가 남의 트레이스 ID 를 끼워 넣을 수 없고, 화면을 다시 열어도 이어진다. 신고와 반응은 하는 일이 달라 API 를 나눈다. 사용자가 추천안을 선택.
다시 볼 조건: 이 변경 전에 저장된 메시지에는 트레이스 ID 가 없어 점수가 붙지 않는다(scored=false 로 응답). 반응 종류가 늘어 점수 이름이 많아질 때.

## 2026-11-02 -- 응답을 닫기 전에 Langfuse 기록을 flush 한다
선택: /api/chat 스트림이 끝날 때(finally), /api/greeting 과 점수를 보낸 직후에 tracing.flush() 를 부른다. 버린 대안: SDK 기본값대로 5초마다 백그라운드로 보내기, Cloud Run 에서 CPU 항상 할당(always-on CPU) 켜기.
이유: staging(00003)에 메시지 7개를 보냈는데 트레이스는 1개만 들어왔다. Cloud Run 은 응답이 끝나면 CPU 를 거의 주지 않아 버퍼에 남은 기록을 보내지 못한다(교안 섹션 7). CPU 항상 할당은 요금이 늘어난다. 응답이 닫히는 시간이 조금 늘어나지만 사용자가 첫 글자를 기다리는 시간에는 들어가지 않는다.
다시 볼 조건: 트래픽이 늘어 flush 시간이 응답 종료를 눈에 띄게 늦출 때.

## 2026-11-02 -- staging 의 LLM 설정을 production 과 맞춘다
선택: friend-agent-staging 에 LLM_PROVIDER=claude, LLM_MODEL=claude-haiku-5-5 를 --update-env-vars 로 더한다(서비스 설정, 코드 변경 없음). 버린 대안: 그대로 두기.
이유: staging 이 모든 메시지에 "답을 만들지 못했어요"를 돌려줬다. 로그와 Langfuse 트레이스 모두 AuthenticationError. staging 은 production 과 같은 llm-api-key(Claude 키)를 쓰는데 LLM_PROVIDER 가 없어 기본값 openai 로 보내고 있었다. 사용자가 추천안을 선택.
다시 볼 조건: staging 과 production 의 모델을 일부러 다르게 시험하고 싶을 때.

## 2026-11-02 -- 소스 배포 빌드는 friend-agent-builder 계정으로 한다
선택: friend-agent-builder 서비스 계정을 만들어 roles/run.builder 하나만 주고, 배포 계정(friend-agent-deployer)은 이 계정 하나에만 iam.serviceAccountUser 를 받는다. deploy.yml 배포 단계 flags 에 --build-service-account 로 저장소 변수 BUILD_SA 를 넘긴다. 버린 대안: squirrel-garden-builder 같이 쓰기, 기본 compute 계정을 대신 쓸 권한 주기.
이유: staging 배포가 "caller does not have permission to act as service account"(기본 compute 계정)로 멈췄다. 기본 compute 계정은 프로젝트 roles/editor 를 갖고 있어, 그 계정을 대신 쓸 권한을 주면 배포 계정이 사실상 편집자가 된다(AGENTS.md 의 넓은 역할 금지). 다람쥐 정원과 같은 방식이고, 앱마다 계정을 나눠 권한이 섞이지 않게 한다. 사용자가 추천안을 선택.
다시 볼 조건: Actions 에서 이미지를 만들어 image 로 배포하도록 바꿀 때(빌드 계정이 필요 없어진다).

## 2026-11-02 -- Langfuse 트레이스는 들어온 요청의 추적 맥락과 끊고 시작한다
선택: chat-turn, greeting 처럼 맨 위 기록을 만들 때 OpenTelemetry 빈 맥락에서 시작한다(tracing.step). 버린 대안: FastAPI 를 내장 계측이 없는 버전으로 고정, 둘 다 하기.
이유: staging 에서 flush 를 넣은 뒤에도 트레이스가 리비전마다 절반쯤 빠졌다. LANGFUSE_DEBUG 로그에서 빠진 요청은 FastAPI 요청 기록과 Langfuse 기록이 함께 만들어지지 않았다. FastAPI 0.162 는 OpenTelemetry 계측이 내장돼 요청 헤더의 traceparent 를 이어받고, Cloud Run 은 요청 일부만 "기록함"(sampled=01)으로 표시한다. 로컬에서 같은 요청에 sampled=00 헤더를 붙이면 트레이스가 사라지고 01 은 들어오는 것으로 재현했다. 맥락을 끊으면 두 경우 모두 들어온다. 사용자가 추천안을 선택.
다시 볼 조건: Langfuse 트레이스를 Google Cloud Trace 와 이어 보고 싶을 때(그때는 맥락을 이어받되 샘플링 판정을 따로 다뤄야 한다). 앞선 "응답 전 flush" 결정은 Cloud Run 의 CPU 제한 때문에 여전히 필요하다.

## 2026-11-04 -- 크레딧 원장: 답을 끝까지 만든 뒤 1 차감, 무료 50개, 위기 메시지는 예외
선택: 메시지 한 턴에 1크레딧을 답을 끝까지 만든 뒤(done) 빼고, 중간에 실패하면 빼지 않는다. 처음 온 사용자에게 무료 50개(ref signup:<user_id>). 잔액이 0이면 /api/chat 이 402 로 거절하되, 위기 표현(safety)이 있는 메시지는 잔액과 상관없이 안전 응답을 보내고 빼지 않는다. 거절 문구는 안내문 말투("크레딧이 부족합니다. 충전 후 이용해 주세요."). "내 데이터 전체 삭제"에서 크레딧 원장은 지우지 않는다. 버린 대안: 메시지를 받자마자 빼고 실패하면 되돌리는 줄 쓰기, 무료 20개·100개, 위기 메시지도 똑같이 거절, 삭제 때 원장도 함께 지우기.
이유: 받은 답만큼만 빠지고 되돌리기 기록이 없어 코드와 테스트가 단순하다. 메시지 원가는 약 1원(Langfuse 기준 건당 약 $0.00075)이라 50개는 원가 약 50원으로 이틀쯤 써 볼 수 있다. 위기 상황인 사람이 크레딧 때문에 안내를 못 받으면 안 된다. 원장을 지우면 삭제를 반복해 무료 크레딧을 다시 받을 수 있다. 사용자가 각 항목을 질문 카드로 골랐다(문구만 추천안이 아닌 안내문 말투).
다시 볼 조건: 잔액 1에서 동시에 보낸 요청이 둘 다 통과해 잔액이 음수가 되는 일이 실제로 생길 때(그때는 받자마자 빼는 방식이나 DB 함수로 바꾼다). 첫인사(/api/greeting) 비용도 크레딧으로 받아야 할 때. 개인정보 처리방침에 결제성 기록 보관을 적어야 할 때.

## 2026-11-04 -- 크레딧 결제: 토스페이먼츠 주문서형 결제(v2), 회원만, 승인까지
선택: 토스페이먼츠 주문서형 결제(v2 에서 "결제위젯"이 주문서형·결제창형 결제로 이름이 바뀜)로 크레딧 묶음 3개(100개 1,000원 / 500개 4,500원 / 1,000개 8,000원)를 판다. 구글 로그인한 회원만 결제할 수 있다. 이번 범위는 주문 저장 → 결제 요청 → 서버 금액 확인 → 결제 승인 → 크레딧 지급까지이고 staging 테스트 키만 쓴다. 주문은 새 테이블 payment_orders 에 저장한다. customerKey 는 회원마다 무작위 UUID 하나를 만들어 주문에 함께 저장하고 다음 결제부터 다시 쓴다. 결제 후에는 같은 화면(/?pay=success, /?pay=fail)으로 돌아와 로그인된 화면이 승인 API를 부른다. 결제 주문과 크레딧 원장은 "내 데이터 전체 삭제"에서 지우지 않는다. 버린 대안: 결제창형, 상품 하나, 게스트 결제 허용, 환불·웹훅까지, 주문 테이블 없이 크레딧 원장만 사용, customerKey 로 ANONYMOUS, 별도 성공·실패 페이지.
이유: 토스 문서(주문서형 결제 연동하기, 결제 흐름 이해하기, LLM Quick Reference)가 결제 요청 전에 주문번호와 금액을 서버에 저장하고 승인 전에 비교하라고 하고, customerKey 에 회원 ID처럼 예측 가능한 값을 쓰지 말라고 한다. 게스트는 브라우저 기록을 지우면 산 크레딧을 잃는다. 같은 화면에서 처리하면 기존 로그인 코드를 그대로 쓴다. 사용자가 질문 카드에서 각 항목의 추천안을 골랐다.
다시 볼 조건: 실제 결제(라이브 키)를 열 때(환불 정책, 웹훅, 전자상거래법 보관 의무, 결제 기록의 개인정보 처리방침 안내). 가상계좌를 결제수단에 넣을 때(웹훅 필수). 승인은 됐는데 저장이 실패한 경우가 로그에 보일 때.

## 2026-11-04 -- 결제 승인 멱등키: 주문마다 UUID v4 하나를 저장해 늘 같은 값을 보낸다
선택: 주문을 만들 때 UUID v4 멱등키를 만들어 payment_orders.idempotency_key 에 저장하고, 그 주문의 승인 요청에는 항상 이 값을 Idempotency-Key 헤더로 보낸다. 승인 요청마다 orderId 와 멱등키를 INFO 로그로 남기고, 시크릿 키와 paymentKey 는 남기지 않는다. 기존 결제 테스트의 가짜 승인 함수에는 멱등키 인자 하나만 더한다. 버린 대안: orderId 를 멱등키로 그대로 쓰기, orderId 로 계산한 UUID v5, 요청마다 새 UUID(이전 코드), 기존 테스트를 그대로 두려고 HTTP 호출을 따로 분리하기.
이유: 토스 문서(인증 및 기타 헤더 설정 > 멱등키 헤더)는 멱등키를 UUID 처럼 충분히 무작위적인 고유 값으로 만들라고 하고, 같은 멱등키의 요청에 첫 응답을 돌려준다. 요청마다 새 값을 만들면 같은 주문을 다시 보낼 때 이 보호를 못 받는다. 0003 마이그레이션은 아직 어디에도 실행하지 않아 칸을 바로 더할 수 있다. 사용자가 질문 카드에서 추천안을 골랐다.
다시 볼 조건: 네트워크 오류나 시간 초과로 승인 결과를 못 받은 주문을 같은 멱등키로 다시 승인하게 만들 때(지금은 그런 주문을 failed 로 바꿔 재시도가 막힌다). 첫 요청 뒤 15일이 지나 멱등키가 만료되는 주문을 다뤄야 할 때.

## 2026-11-04 -- 결과를 모르는 승인 실패는 주문을 ready 로 남기고 같은 멱등키로 다시 승인한다
선택: 네트워크 오류·시간 초과, 토스 5xx, 409 IDEMPOTENT_REQUEST_PROCESSING 은 "결과를 모르는 실패"로 보고 주문을 failed 로 바꾸지 않는다. 서버가 같은 요청 안에서 같은 멱등키로 1초, 2초 뒤 두 번 더 시도하고, 그래도 안 되면 503 {"retry": true} 를 돌려준다. 화면은 "결제 확인 다시 시도" 버튼으로 같은 승인을 다시 보낸다. 카드 거절 같은 나머지 4xx 는 지금처럼 failed. 이 때문에 앞서 만든 승인 실패 테스트에서 토스 500 경우를 빼고 tests/test_payment_retry.py 로 옮겼다. 버린 대안: 네트워크 오류만 재시도, 화면 버튼만, 서버 자동 재시도만.
이유: 토스 에러 코드 문서는 500 에 "잠시 후 다시 시도"를, 멱등키 문서는 409 IDEMPOTENT_REQUEST_PROCESSING 을 이전 요청 처리 중으로 안내한다. 이런 경우 토스에서 실제로 승인됐을 수 있어서 failed 로 끝내면 돈은 빠지고 크레딧은 안 들어간다. 같은 멱등키로 다시 보내면 토스가 첫 응답을 돌려줘 두 번 결제되지 않는다. 사용자가 질문 카드에서 추천안을 골랐다.
다시 볼 조건: 인증 뒤 10분이 지나 재시도도 못 하는 주문이 생길 때(결제 조회 API나 웹훅으로 결과를 확인해야 한다). 재시도 대기 때문에 승인 응답이 너무 늦어질 때.

## 2026-11-04 -- 로컬 개발(ENV=local, AUTH=none)에서는 개발용 사용자가 토스 테스트 결제를 시험할 수 있다
선택: 결제는 회원만이라는 규칙에 예외 하나를 둔다. ENV=local 이고 AUTH=none 이면 개발용 사용자(local-user)도 결제 API를 쓸 수 있다. 화면도 같은 조건에서 충전 화면을 연다. staging·production·test 환경의 게스트는 지금처럼 403. 버린 대안: production 이 쓰는 Supabase 프로젝트로 로컬 테스트하기, 시험용 Supabase 프로젝트와 구글 로그인을 먼저 만들기.
이유: 사용자가 "최대한 편하게"를 요청해 추천안(직접 할 일이 가장 적은 방법)으로 정했다. AUTH=none 의 사용자는 로그인 기능이 없는 개발용 한 명이라 "기록을 지우면 크레딧을 잃는 게스트"와 다르다. 이렇게 하면 .env 에 토스 테스트 키 두 줄만 넣으면 실제 토스 테스트 결제를 확인할 수 있고, production DB에 테스트 데이터가 섞이지 않는다. 설정 검사(config.py)가 STORAGE=supabase 와 AUTH=none 조합을 막아 이 예외는 메모리 저장소에서만 동작한다.
다시 볼 조건: staging 을 AUTH=none 으로 두고 ENV 값을 local 로 바꾸는 일이 생길 때(그러면 공개된 서비스에서 누구나 결제 API를 쓸 수 있다). 시험용 Supabase 와 구글 로그인이 준비돼 실제 회원 흐름으로 테스트할 수 있을 때.
